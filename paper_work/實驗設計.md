## 1. 設計原則

### 1.1 核心認知：本專題有**兩個獨立的驗證**，不是一個

| | 驗證什麼 | 需要什麼 | 指標 | 可用真實資料驗證？ |
|---|---|---|---|---|
| **軌道 A：預測** | 模型預測車速準不準 | 真實時序資料 | MAE / RMSE / MAPE | ✅ 可以 |
| **軌道 B：決策** | 全域懲罰能否抑制羊群 | 路網 + OD 需求 + 壅塞模型 | ATT / Gini / worst-ρ | ❌ **本質上不行** |

**軌道 B 為何無法用真實資料驗證**（此為方法論的必然，非本專題的妥協）：

1. **沒有真實 OD 資料**——TDX 提供的是「路段速度」，不是「誰從哪裡到哪裡」。
2. **需要反事實（counterfactual）**——要證明「抑制了羊群」，必須比較「若這 800 台車改走別條路會如何」。真實世界不提供平行時空。

因此軌道 B 的正確做法是：**環境用真實的（路網拓樸、速限、TDX 車速、車道數→容量），需求用合成的，並在完全相同的環境與需求下比較各策略**。這是交通模擬研究的標準做法（SUMO 類研究皆然），在報告中應主動說明，而非迴避。

### 1.2 被排除的方案與理由

曾考慮但排除的兩個方案，皆因**預測模型無法跨路網遷移**：

| 模型 | 節點數綁定處 | 後果 |
|---|---|---|
| STGCN | `nn.LayerNorm([n_vertex, channels])`（`layers.py:246`）＋ spectral GCN 綁定固定 Laplacian | 設計上即為 transductive |
| STGAT | 逐節點 `nn.Parameter(torch.zeros(num_nodes, out_features))`（`stgat.py:37`）＋ `BatchNorm2d(num_nodes)`（`stgat.py:80`） | GAT 理論上可 inductive，但此實作被逐節點參數破壞 |

→ **以 207 節點訓練的權重無法載入不同節點數的模型（shape mismatch）**，故「METR-LA 訓練預測 → 直接套用台中路網」不可行。計畫書 §5 的 zero-shot 遷移主張在現有實作下不成立；改以 §4.3 的 **fine-tune 對照實驗**（A3）取代並驗證。

### 1.3 ★ 三層路網架構（v4 新增）

v3 假設「一張裁切後的路網同時服務預測與決策」。實作後發現**兩者對地圖大小的需求相反**：

| | 需要什麼 | 為什麼 |
|---|---|---|
| **軌道 A（預測）** | 地圖**越大越好** | 預測的圖建在 **TDX 路段**上，地圖只決定「哪些路段通過 map-matching」與高斯核的路網距離。地圖小 → 通過匹配的路段少 → **`n_vertex` 永久受限，事後換大地圖也補不回來** |
| **軌道 B（決策）** | 場域**要小且集中於 TDX 走廊** | RL 的 credit assignment 隨路徑長度惡化；且覆蓋率的分母是場域邊數 |

因此改為三層，各司其職：

```
① 完整圖   Map_fined  39,920 節點 / 43,711 段（1,748.8 km）   ← 原始交付，Demo 繪圖
      │ build_simplified_network.py：依 oneway 展開 → 取最大 SCC → 合併中途節點
      ▼
② 簡化圖   9,904 節點 / 27,022 有向邊                          ← 軌道 A 的 map-matching 與路網距離
      │ build_arena.py：主幹道種子 → 走廊 → 連通補齊 → 再簡化
      ▼
③ 實驗場域 840 節點 / 1,690 有向邊                             ← 軌道 B 的訓練與評估
```

> **節點 id 全程沿用原始 OSM id**，故場域上算出的路徑可直接畫在①的完整地圖上，Demo 不需另做對應。

### 2.4 鄰接矩陣建構

沿用計畫書 §4.2：Gaussian kernel 加權
$$W_{ij} = \exp\left(-\frac{d_{ij}^2}{\sigma^2}\right) \text{ if } d_{ij} \le \kappa$$

其中 $d_{ij}$ 為**沿道路的最短距離**（非歐式直線距離）——以 Dijkstra 在**簡化圖（9,904 節點）**上計算，符合計畫書「以路網距離計算」的要求。

**距離門檻 κ 的決定方式**：原始實作未套用 `if d_ij ≤ κ`，導致鄰接矩陣**全部非零（100% 稠密）**；全連通會讓 graph convolution 在所有節點上平均，**稀釋空間結構**。現改為**自動挑選 κ 使鄰接密度對齊 METR-LA**：

| | 節點數 | σ | κ | **非零比例** |
|---|---|---|---|---|
| METR-LA（參照） | 207 | — | — | **37.3%** |

#### ★ `build_simplified_network.py` 的三個設計要點（v4 新增）

`Map_fined` 的節點粒度極細（每 ~44 m 一個節點），其中 **73.2% 是「一進一出」的中途節點**——逐節點決策的 policy 在那裡沒有選擇可做，卻要付出一次決策、一次編碼、一次 PPO transition。

1. **先依 `oneway` 展開再判斷中途節點**——節點算不算「中途」取決於方向。
   盲目雙向化會憑空生出約三分之一的逆向邊，讓分流看起來比實際容易。
2. **速限用「長度加權調和平均」** $S = \sum \ell_i / \sum (\ell_i / v_i)$——**唯一能讓 `t0` 完全不變的算法**。算術平均或取最小會讓全網每條邊的 `t0` 悄悄偏移。
3. **輸出改為一列一條有向邊**——`taichung_loader.py` 不讀 `oneway` 欄，沿用「一列一路段」會讓它把每條路都當單行道。

**內建正確性證明**：比對原圖與簡化圖之間 **300 組 OD** 的自由流最短路徑時間，實測**最大相對誤差 1.51e-15**（機器精度）、0 組不可達；超過 `1e-6` 直接 `exit 1`。另設「不可達比例 > 2% 直接失敗」的連通性硬檢查。

> **為何需要第二道檢查**：第一版的孤兒環偵測把**被正確合併掉的鏈中間節點**誤判成孤兒又加回去，
> 等於撤銷簡化（300 組 OD 有 248 組不可達），卻仍印出 `PASS`。
> **檢查只跑在沒壞的部分上，會給出假的通過訊號。**

1. **固定權重集成幾乎沒有效益**——最佳集成只勝過單獨 STGAT 0.40%，落在雜訊範圍內。
2. **兩模型錯在同樣的地方**（誤差相關 0.934）。集成獲益的前提是誤差不相關。
3. 🔴 **MAE 最佳權重（0.20）與 RMSE 最佳權重（0.65）落在光譜兩端**——STGCN 誤差變異較小（少犯大錯），STGAT 典型誤差較小（平均較準）。**單一全域常數必須在「平均準」與「不犯大錯」之間二選一。**

> $$\text{Fusion}(s,t)=\tanh\big(W_2 \cdot t \cdot \text{gate} + (I-\text{gate}) \cdot W_3 \cdot s\big),\quad \text{gate}=\sigma(W_1(s+t))$$
> 實作策略：先快取兩模型在全資料集的預測，再訓練輕量 fusion head（成本低、不需重訓主模型）。

**固定權重定案為 `0.2/0.8`，並已在測試集確認（v5 新增）**：

| 誤差相關 | 0.934 | **0.908** |

**權重沒有過擬合驗證集**，而且 MAE 與 RMSE 的最佳點**第三次**落在光譜兩端
（175 val、202 val、202 test）。§18 掛了很久的「尚未在測試集確認」至此結案。

⚠️ **`0.2/0.8` 使融合結果 ≈ STGAT，因此決策層基準 ④（hybrid）與 ③（STGAT）幾乎相同**。
已驗證**不是程式錯誤**：hybrid 重建的最大誤差 5e-6、corr(hybrid, stgat)=0.9991、
corr(stgcn, stgat)=0.9712、兩者中位相對差 0.62%。這是權重的必然結果。

### 3.6 ★ HA 基準與三個關於資料性質的發現（v5 新增）

計畫書 §4.6 明文要求「與 STGCN、STGAT、**HA（Historical Average）** 比較」。
`integration/ha_baseline.py`（新增）**不需 checkpoint、不需 GPU、不需推論**——純從資料算：

$$\text{HA}(i, r) = \text{mean}\{\, v_{i,r'} : r' \in \text{train},\ \text{dow}(r')=\text{dow}(r),\ \text{tod}(r')=\text{tod}(r),\ \text{mask}_{i,r'}=\text{True} \,\}$$

7 × 288 時槽 × 202 路段，**只用 train 的真實觀測**。每個有值的格平均 14.2 個觀測；
6.98% 的格在 train 沒有任何真實觀測，回退到該路段的 train 平均。

**兩個容易靜默出錯的地方**：

| | 陷阱 | 處置 |
|---|---|---|
| **時區** | 時間戳是 UTC。重貼時槽標籤不改變 MAE，但**星期的邊界會偏 8 小時**，把週一凌晨併進週日——而尖峰正是平日現象 | 全程以 UTC+8 計算 |
| **視窗** | 分數要能與 STGCN/STGAT 並排，就必須落在**完全相同的目標列**上 | 內建 persistence 交叉驗證：算出來必須與 `evaluate_masked.py` 吻合，否則 `exit 1` |

**交叉驗證三個時程全部 `+0.00%`**（4.2872 / 4.6744 / 5.1281）。

#### ① 🔴 模型的「領先幅度」方向會隨對照基準翻轉

```
相對 persistence   −21.1% / −24.8% / −29.2%   ← 領先隨時程「擴大」
相對 HA            −16.5% / −13.2% / −10.4%   ← 領先隨時程「縮小」
```

兩個都是真的。但**只引用 persistence 那組會高估長時程的優勢**——那主要是 persistence
在變爛（4.29 → 5.13），不是模型在變好。HA 與時程幾乎無關（4.0486 → 4.0496）。

> **報告寫法**：**三個時程都必須同時列 HA 與 persistence。**
> 兩個基準的失效方式相反——persistence 知道當下卻不知道結構，HA 知道週間結構卻不知道今天。
> **只贏其中一個是弱證據**；兩個都贏，才證明模型同時用了「當下觀測」與「學到的時空結構」。

#### ② HA 在三個時程都贏 persistence，包括 15 分鐘

與一般交通預測文獻的直覺相反。原因是**本資料集的補值**：persistence 的輸入
`vel[rows − n_pred]` **那一格本身很可能是 ffill 補值**（整體 24.6%）。
旁證：HA 的 unmasked MAE 5.31 遠差於 masked 4.05——補值格對 HA 特別難。

#### ③ 🔴 尖峰是最「規則」的時段，而 STGCN 在那裡輸給 HA

### 3.7 ★★ Gated Fusion：計畫書 §4.3 的雙路架構（v5 新增）

```
gate   = σ( W₁ · (s + t) )
Fusion = tanh( W₂ · t · gate + (I − gate) · W₃ · s )
output = FC(Fusion)  →  15 / 30 / 60 分鐘
```

`s`、`t` 是兩條 path 的**隱藏特徵**——計畫書把融合放在骨幹與輸出頭之間
（若 s、t 已是最終速度，後面那層 FC 就沒有存在的理由）。

#### ① 三層落差：兩條管線沒有一處相同

| | STGCN | STGAT |
|---|---|---|
| **視窗數（test, p12）** | **7,518** | **7,539** |
| 輸入形狀 | `[B, 1, 12, N]` | `[B, N, 12, 2]` |
| 第二通道 | 無 | **time-in-day**（UTC+8 的日內比例） |
| **正規化** | **逐路段** z-score | **單一全域純量** z-score |
| 輸出 | 單步 | 十二步 |

**但視窗定義其實相同**：令 `g = i = t−11`，兩者都是「輸入 `g..g+11`，時程 p 的目標在
`g+11+p`」。視窗數不同只是修剪切分邊界的方式不同。
**正規化則不能統一**——拿全域尺度的輸入餵逐路段尺度訓練的 STGCN，**不報錯，只輸出垃圾**。

#### ② 實作定案：聯合訓練 + 補 STGCN 的 time-of-day

`fusion/`（新增，1,241 行）以**別名**把兩個 `model/` 套件載進同一 process
（兩個 repo 都有同名套件），並提供一份統一的 dataloader，從同一批列產生**兩個**張量。

| | 凍結骨幹 | 聯合訓練（**採用**） |
|---|---|---|
| 能否突破誤差相關 0.934 | ❌ 兩個凍結的骨幹錯在同樣的地方 | ✅ gate 給了兩條 path 分工的理由 |
| 一個模型三時程 | ❌ STGCN 骨幹綁定單一時程 | ✅ 新的 FC 頭直接吐 12 步 |

⚠️ **補 time-of-day 不算偏離計畫書**——§4.3 白紙黑字要求 STGCN Path 萃取
「尖峰時段、星期週期」，而那正是 time-of-day 定義的東西。現有實作是漏了。

#### ③ 🔴 管線驗收：先證明等價，再訓練

### 3.8 ★★★ A3-a：計畫書 §5 的 zero-shot 遷移不成立（v6 新增）

並在 **fine-tune 數個 epoch 後**達到可用水準。」兩個宣稱分開測；本節是前半，

#### ① 95.6% 的參數其實搬得過去

> 可用訊號，**最好的變體是完全沒有遷移的隨機初始化**。

#### ④ ★ 「輸給隨機」的正確讀法

隨機網路輸出**近似常數**（曲線平坦，MAE ≈ 平均絕對離差 ≈ 7.4），它**什麼都沒說**，
所以是安全的；遷移過來的網路會**說出結構化但錯誤的東西**，那可以比常數更差。

> **因此結論是「遷移過來的表徵在目標路網上是主動錯位的」，不是「沒有攜帶資訊」。**
> 報告要用這個版本——它比「遷移失敗」更精確，也更禁得起追問。

#### ⑤ ⚠️ 一個被推翻的假設，與兩個必須揭露的界線

B 的爆炸有乾淨的機制解釋（fresh BN 的 `running_var=1` 等於不正規化，而權重期待 0.70–5.70），
據此做了 AdaBN 式校準——**結果從 10.64 惡化到 69.53，假設被推翻**。
可能與 `GraphAttentionLayer` 的 dropout 0.6 下累積的統計量有關，**未驗證且不追**：
四個變體的差別只在「正規化壞得多嚴重」，不在「遷移了多少知識」。

| 界線 | 內容 |
|---|---|
| **zero-shot 的定義** | 「**沒有對台中做任何梯度更新**」，不是「完全沒碰台中資料」——z-score 的 mean/std 來自台中 train split（兩城市單位不同，來源的統計量無意義）。**報告要寫明** |
| **D 那一列的標籤** | 若引用，必須標成「**zero-shot + BN adaptation**」，不是純 zero-shot |

### 3.9 ★★★ A3-b：fine-tune 成立——收斂快 3.3 倍，終點打平（v6 新增）

`train.py --init-from`，**除此之外每個旗標都與 A2 逐字相同**（lr 3e-4、epoch 500、
early_stop 40、batch 100、SmoothL1、StepLR(10, 0.9)）。唯一的差別是初始化。

| | 最佳 epoch | 總 epoch | 牆鐘 | 15 min | 30 min | 60 min |
|---|---:|---:|---:|---:|---:|---:|
| **A2 從頭訓練** | **23** | 64 | 4024.6 s | **3.3802** | **3.5127** | **3.6276** |
| **A3-b fine-tune** | **7** | 47 | 3941.9 s | 3.4137 | 3.5304 | 3.6510 |
| **Δ** | **−70%** | −27% | −2% | +0.99% | +0.50% | +0.64% |

依事先寫下的判準：**終點中性**（三個時程全在 1% 門檻內）、**速度大幅改善**（7 vs 23）。

> **計畫書 §5 的兩個宣稱：前半（zero-shot）不成立，後半（fine-tune）成立。**
> 「在 **fine-tune 數個 epoch 後**達到可用水準」——**七個 epoch 就是「數個 epoch」。**

#### ★★ 一個值得寫進報告的張力

**同一份初始化，zero-shot 比隨機還差（8.76 vs 7.37），卻讓 fine-tune 的最佳 epoch
從 23 掉到 7。** 這不矛盾：**遷移過來的權重是很差的預測器，卻是很好的起點**——
它落在參數空間中一個離目標解很近的區域，儘管它當下算出來的函數是錯的。
**「能不能直接用」與「好不好學」是兩件事**，而計畫書把它們寫成同一句話的兩半。

#### ⚠️ 三個限制，其中一個是本節最弱的一環

| | |
|---|---|
| 🔴 **兩次都是無種子的單次執行** | `STGAT/train.py` 直到 08-31 才有 `--seed`（STGCN 與 fusion 一直都有，預設 42）。23 → 7 看起來遠大於雜訊，**但 n=1 無法嚴格宣稱**。要釘死需拿 A2 跑數個種子測 best-epoch 的自然變異（P15） |

| **收斂更快，但高原略高** | 三個時程一致略差 0.5–1%，符合「預訓練把你快速丟進一個盆地，但那個盆地略淺」 |

#### 🔴 量測一：負載佔比完全預測不了衝擊

同一批 766 台車、同一組參考邊，**從頭封閉**（衝擊上界）：

| 封閉 | 邊數 | 基準負載佔比 | ATT | ΔATT |
|---|---:|---:|---:|---:|
| （未封閉） | 0 | 0.00% | 723.3 | +0.0% |
| **臺灣大道（整條）** | 83 | 8.81% | 1479.8 | **+104.6%** |
| 臺灣大道二段 | 36 | **6.32%** | 757.3 | **+4.7%** |
| **臺灣大道三段** | 20 | **2.24%** | 1467.7 | **+102.9%** |
| 臺灣大道四段 | 5 | 0.00% | 723.3 | +0.0% |

**最忙的二段關掉只 +4.7%；最不忙的三段之一卻造成 +102.9%。**
三段是咽喉，二段有好的平行道路。

> **教訓**：「這條路多重要」不能用它承載多少流量判斷，要看**移除它之後替代路徑貴多少**。
> 與 §5「按長度的覆蓋率才是有效的那個」同型——用一個看似合理的代理量去排序而排錯。

#### 🔴 量測二：`--close-at` 高度非線性，且 Gini 的方向會反轉

| `--close-at` | ΔATT | ΔGini |
|---|---:|---:|
| 0.00 | **+104.6%** | **+5.9%** |
| 0.10 | +90.5% | +3.7% |
| 0.25 | +50.3% | +1.0% |
| 0.50 | +17.1% | **−2.3%** |
| 0.75 | +2.2% | **−2.5%** |

ATT 掉這麼快是 BPR 的四次方項——替代道路上的車少一半，超額延誤就少約 2⁴ = 16 倍。

🔴 **但 Gini 在 0.5 之後反而下降**：封閉把車流切成兩組不同的路線集合，
負載攤在更多邊上，**比大家都走同一條路還平均**——封閉本身當了一次粗糙的負載平衡器。

> **這修正了 v4 的期待。** v4 §10 曾寫「S3 是唯一可能讓 Gini 達標的路」。
> **只有早期封閉才會拉高基準 Gini**，而 §4.7 的實測進一步顯示：即使 `--close-at 0.10`，
> **oracle 自己的 Gini 改善反而略差**（−18.1% → −17.4%）。**S3 放大 ATT，救不了 Gini。**

#### 🔴 量測三：封閉後的斷裂是「場域裁切的假象」

```
場域 840 節點   → 關臺灣大道 → 最大 SCC 780（92.9%），60 個節點掉出去
完整路網 9,904 → 關同一條路 → 最大 SCC 9,823（99.2%）

★ 掉出去的 60 個節點裡，57 個（95%）在完整路網上仍然連通
```

若把那 3.8%±0.5% 的行程計為「封閉造成的未送達」，等於**把 `build_arena.py` 的裁切決策
當成研究發現**，而且會讓 ⑦ 掉到 95% 門檻以下、整列被標 `NOT COMPARABLE`。

**定案：`--close-demand filter`**——沿用 S2 **完全相同**的需求，只排除封閉後不可行的行程。
4 個 hub 跨 10 seeds 相同且全部存活。**報告須揭露這個排除與它的依據。**

> **為何整批過濾而非分波過濾**：整批過濾讓需求**與 `--close-at` 脫鉤**，
> 封閉時機的敏感度分析才能配對比較。

### 4.4 壅塞模型與容量校準### 4.4 壅塞模型與容量校準

**BPR volume-delay**（SUMO 接入前的代理）：
$$t_e(\text{load}) = t_0\left(1 + 0.15\left(\frac{\text{load}}{\text{cap}}\right)^{4}\right)$$

**容量校準**：CSV 容量為 veh/h（1,360–8,158），與模擬的車輛數尺度不符——直接使用會導致 ρ≈0、完全不壅塞、無羊群可抑制。以 `calibrate_taichung.py` 掃描，選定 `(n_vehicles, capacity_scale)` 使**羊群基準的 worst-ρ 落在 2–3.5**（確保有壅塞可抑制，但未完全癱瘓）。

| 場域版本 | `capacity_scale` | 800 車下的羊群基準 worst-ρ |
|---|---|---|
| 完整路網（20,390 邊） | 0.0400 | ~3.0 |
| 1,224 節點場域 | 0.0441 | — |
| 1,442 節點場域 | 0.0414 | 3.46 |
| **840 節點場域（定案）** | **0.0429** | **3.33 ± 0.27（10 seeds）** |

> ⚠️ **車輛數改變就必須重跑校準**。0.0429 只對應 800 車。

| # | 策略 | 用預測？ | 協調？ | eq.4？ | 對應計畫書 |
|---|---|:--:|:--:|:--:|---|
| ① | `static`（自由流 Dijkstra） | ✗ | ✗ | ✗ | 基準 ① |
| ② | `stgcn + Dijkstra` | ✓（純 STGCN） | ✗ | ✗ | 基準 ② |

**設計說明**：
- **④ 為 Δ 的比較基準**——它代表「所有車都看同一份預測、各自貪婪選最快路」，這正是羊群效應的定義。
  **v5 起 ④ 吃的是 gated fusion**（§3.7），與計畫書所述的架構一致。
- **⑥ 是 oracle，不是本系統**。它使用全域 Dijkstra + 精確全域負載 + 每批重算全圖。報告中須明確定位為「**eq.4 目標的實用上界**」。
  > 🔴 **v6 更正**：這裡原本寫 ⑥ 的能力是「DRL 刻意不擁有的」，語意上暗示它昂貴。
  > **實測相反**——⑥ 一次請求只要 **0.31–0.33 ms**，比 ⑦ 快 43–68 倍（§9.2 ③）。
  > ⑥ 真正的優勢不是資訊也不是算力，而是**環境的成本函數（BPR + eq.4）就是它自己**：
  > 它是那個函數的直接最佳化器，不是近似。**⑦ 落後是結構上的必然，而非算力或資訊的取捨。**
- ✅ **③④ 的簡併已被 fusion 打破**（v4 是 `+0.0±0.0%`，即路徑逐條相同；v5 是 `+0.8±0.7%`）。
  §4.8 曾預測「要讓 ③④ 分開，得先讓兩個模型的預測真正不同」——應驗了。

#### ★ ⑦ 一律報告兩列：貪婪解碼與 beam-8 解碼（v5 新增）

**同一組權重、同一份觀測，只有解碼方式不同**，所以每一條邊仍由 πθ 提出並評分——
這是**解碼方式的消融，不是換一個決策者**（基底論文 Lei et al. 2022 的比較表本就並列 `G / BS`）。

- 展開依**累積 log 機率**（policy 自己的偏好），最終在已完成的候選中依**實際 eq.4 成本**挑選。
  若連搜尋過程都用成本排序，就變成成本導引的搜尋，而非「把 policy 讀得更寬」。
- `test_beam.py`（新增）驗證**寬度 1 逐節點等於貪婪**——這是任何 beam 數字可信的前提。

**Beam 修好的是完整性，不是路由品質**：dead-end S2 36.8 → 0.5、S3 132.4 → 29.6，
但無封閉時加寬 4 倍只讓 ATT 動 0.8%，且 10 seeds 的 headline **變差**（−38.4% → −36.0%），
因為救回來的是昂貴的行程。

> 🔴 **v6 新增：beam-8 的第三個代價是延遲，而它打破計畫書 §5。**
> 解碼器每跳對**每條 live beam** 各發射一次，每車 218–261 次（貪婪只有 23 次）。
> 單車端到端 GPU 90–104 ms、CPU 44–51 ms——**四種組合全部超過 50 ms**（§9.2）。
>
> **因此引用規則要拆成兩半**：**品質引用 beam-8、延遲引用貪婪**，
> 並**在同一段裡點明這是兩個設定**。各取所需地分開報，是最容易被口試抓的寫法。
>
> 工程上有解但未實作：8 條 beam 合成一次 forward，估可降到 ~35 ms（§9.2 ②、P14）。

**待決定的第八列**：計畫書要求輸出 15/30/60 三個時程。fusion 完成後一次 forward 就有三個時程，
**⑦a（單時程）vs ⑦b（三時程觀測）的消融終於可行**，但會多一次完整 DRL 訓練。

### 4.6 指標（計畫書 §4.6）

| 指標 | 定義 | 方向 |
|---|---|---|
| **Served %** | 成功抵達比例 | ↑ |
| **ATT** | 所有車輛平均通行時間 | ↓ |
| TSTT | 系統總通行時間 | ↓ |
| **Gini(邊負載)** | 邊負載分佈的 Gini 係數——**量化羊群抑制程度的核心指標** | ↓ |
| **worst-link ρ** | 最壅塞路段飽和度 | ↓ |
| Throughput | 單位時間完成行程的車輛數（代理：served / ATT） | ↑ |

**評分規則**：所有策略的路徑產出後，**一律在同一個 BPR 模型下重新評分**；Gini 以「所有策略用過的邊」聯集為參考集合（確保可比）。

#### 🔴 三項守門（皆針對「不報錯的錯」）

| # | 守門 | 防什麼 |
|---|---|---|
| 1 | **`.meta.json` sidecar** | 任何「會改變模型輸入或 policy 觀測」的設定，存檔時一併寫出、讀檔時自動套用並比對。已用於預測輸出（`taichung_pred_*.meta.json`）與 DRL checkpoint（`togo_refresh` / `reward_scale` / 各 mult / `capacity_scale`）。**訓練與評估設定漂移不會報錯，只會靜默讓結果變差。** |
| 2 | **`served%` 為第一欄 + `MIN_SERVED=0.95` 標記** | served 不同的策略，ATT 根本不可比（見下）。低於門檻的列印出 `NOT COMPARABLE` |
| 3 | **`congestion_note()`（`CONGESTION_BAND=(1.5, 5.0)`）** | 若羊群基準的 worst-ρ 落在區間外，代表校準失效、整份比較沒有意義 |

#### 🔴🔴 一個放棄困難任務的策略，可以「贏過」理論上界（v5 更新）

不同策略放棄的行程數不同，而**被放棄的行程確實較難**。v4 用共同子集估計，
v5 用 beam search 把行程救回來後**直接量到**：

```
S3   ⑦ 貪婪    ATT −63.0%   (served 82.8%)
     ⑥ oracle  ATT −61.2%   (served 100%)     ← 貪婪「打贏」了理論上界
     ⑦ beam-8  ATT −55.8%   (served 96.0%)    ← 修正後，如預期落後 oracle
```

**灌水幅度隨放棄率放大**：

```
S2   放棄  4.6%  →  ATT Δ 灌水  2.4pp
S3   放棄 17.2%  →  ATT Δ 灌水  7.2pp   ← 足以翻過 oracle
```

> **這是守門 2 存在的最強證據。** 沒有它，報告會出現「本系統優於理論上界」這種
> **必然錯誤**的結論，而表格本身不會有任何異狀。
>
> **報告寫法：⑦ 一律引用 beam-8 那一列**，貪婪列為消融並註明其 served%。

⚠️ 注意 `metrics.evaluate()` 會丟掉失敗的行程，導致索引與需求錯位——
`diagnose_agent.py` 因此自備 `realized_times()`，不可直接重用前者做子集比較。
**且多個 agent 必須在同一次執行裡比**：分開跑的共同子集不同，實測兩次差 8 台車就讓
static 的 ATT(common) 移動 3.7%——**比要找的效果還大**。

⚠️ **Gini 以「所有策略用過的邊」為參考集合，所以多加一列策略，每一列的 Gini 都會微幅移動**
（ATT 與 worst-ρ 不受影響）。**跨執行引用 Gini 前，先確認兩次的策略集合相同。**

### 4.8 ★ agent 與 oracle 差距的歸因（v4 新增）

`diagnose_agent.py` 把三個常被混淆的原因分開：**繞路 / 壅塞 / 折損（attrition）**。

| 策略 | served | 繞路比 | p90 | ATT(all) | **ATT(common)** |
|---|---:|---:|---:|---:|---:|
| ① static | 799 | 1.000x | 1.000x | 790.1 | 758.8 |
| ④ hybrid | 799 | 1.012x | 1.035x | 810.8 | 778.3 |
| ⑤ load-aware | 799 | 1.029x | 1.045x | 477.2 | 467.9 |
| ⑥ oracle | 799 | **1.131x** | 1.366x | 464.9 | **456.4** |
| ⑦ DRL | 774 | **1.096x** | 1.278x | 518.4 | **518.4** |

1. **oracle 繞得比 load-aware 更多，ATT 卻更低**——繞遠路本身不是問題。
2. **agent 繞得比 oracle 少，同一批行程卻慢 13.6%**——「過度繞路」的假設**被否證**；症狀是**選進壅塞區**。

**機制**：`_dist_to_dest` 原本以 `weight="t0"` 計算「還有多遠」，而該值餵給候選特徵、A\* 提示 `to_go`、E-GAT 節點特徵與 potential shaping——**agent 看得到下一跳的 ρ，卻看不到那一跳之後的路況**。差別**不在資訊新鮮度**（agent 的 ρ 比 oracle 更新），**而在前瞻**。

**修正 `--togo-refresh K`**：`_dist_to_dest` 改用 `_gcost`（與獎勵同一個成本函數）當權重，每 K 台車重算。快取依目的地，hotspot 僅 4 個 hub → 800 車 K=25 只需 128 次 Dijkstra。

以解析式 agent（`GreedyOracleAgent = argmin(gcost + to_go)`）驗證機制：

```
togo_refresh=0   (自由流 to-go)     served  94/799   1.01s
togo_refresh=25  (eq.4 成本 to-go)  served 575/799   1.43s      ← 送達率 6 倍，成本 +42%
```

⚠️ `togo_refresh` **改變 policy 讀到的觀測，不能只在評估時開啟**——必須重訓，由 sidecar（§4.6 守門 1）強制。

#### ⑤ 重訓結果：機制確認，但確認的是「繞路的量」（v5 新增）

同一批 741 台車、同一次執行（跨 agent 比較必須如此，見 §4.6）：

| 策略 | 繞路比 | p90 | ATT(common) | **離 oracle** |
|---|---:|---:|---:|---:|
| ④ 羊群基準 | 1.012x | 1.035x | 773.4 | 72.7% |
| ⑤ load-aware | 1.029x | 1.044x | **460.0** | **2.7%** |
| ⑥ oracle | **1.128x** | **1.360x** | 448.0 | 0.0% |
| ⑦ 舊 agent（`togo_refresh=0`） | 1.095x | 1.279x | 510.9 | 14.1% |
| **⑦ togo25** | **1.127x** | **1.361x** | **499.6** | **11.5%** |

**判準通過**：ATT(common) 510.9 → 499.6，**縮小 18% 的 oracle 差距**。
10 seeds 上 worst-ρ 也因此由 −19.8% 推到 −27.2%，**跨過計畫書門檻**。

#### ⑥ ★★ 但最尖銳的發現是：繞路的「量」對上了，「質」沒有

```
繞路比   togo25 1.127x  ≈  oracle 1.128x     ← 逐位相同
p90      togo25 1.361x  ≈  oracle 1.360x     ← 逐位相同
ATT      togo25  499.6  vs  oracle  448.0    ← 仍差 11.5%
```

更關鍵的對照：**⑤ load-aware 只繞 1.029x，ATT 卻是 460.0——比繞 1.127x 的 agent 還好。**

> **繞得跟 oracle 一樣多是不夠的，要繞到對的地方。**
> to-go 的修正給了 agent 正確的「繞多少」，但沒有給它「繞去哪」。

**這把剩餘差距定位得很精確**——不是 λ 權重（§4.7 ③ 已用 oracle 否證）、
不是繞路幅度（現在逐位對上）、而是**在給定的繞路預算下選哪一條路徑**。

#### ⑦ beam search：v4 的暫緩理由失效，但結論仍是「修不好品質」

v4 曾以「指南針偏了，加寬搜尋只會找到更多同樣偏差的路徑」暫緩 beam search。
**指南針對準之後那個理由不成立**，所以 v5 實作並量測了它：

- **修好完整性**：dead-end S2 36.8 → 0.5、S3 132.4 → 29.6，⑦ 在兩個情境下都完全可比
- 🔴 **修不好品質**：無封閉時加寬 4 倍只讓 ATT 動 0.8%；10 seeds 的 headline **變差**
  （−38.4% → −36.0%），因為救回來的是昂貴的行程

> **所以離 oracle 的 11.5% 是模型誤差，不是搜尋誤差。** v4 的推測被**否證**。
> beam search 買到的是**完整性**（也就是誠實的數字），不是路由品質。

### 4.9 ★★★ eq.4 權重掃描：計畫書 §4.4 的 grid search（v6 新增）

計畫書 §4.4 要求「α, λ₁, λ₂ 以 **grid search 在驗證集上調整**」，**此前從未執行**。
而報告最顯眼的未達標（Gini）的辯護正好是「非學習不足而是情境結構」——**那是論證**。
本節把它變成量測，並推翻它原本給的理由。

#### 三個方法決定

| | |
|---|---|
| **只掃 λ₂，只看 ⑥** | λ₂ 進入 ⑤⑥ 的解析成本與 ⑦ 的獎勵；①~④ 不讀它。改 λ₂ 對 ⑥ 零成本，對 ⑦ 每個值要重訓 13 h。而 ⑥ 正是報告那句話的主詞——**eq.4 的解析最佳化器**若到不了，這個目標本身就到不了 |
| **α 不掃，且可證明無需掃** | `α·BPR + t_ref·scale·(λ₁·overflow + λ₂·spread)`，同乘 k > 0 只讓成本乘 k，**Dijkstra 的 argmin 對正純量不變**。只有比值有意義，固定 α=1 掃 λ **不損失一般性** |
| 🔴 **Gini 的參考邊集合必須跨 cell 固定** | 逐次聯集會隨 λ₂ 變大（⑥ 繞到更多邊上），**連分母 ④ 的 Gini 都跟著動**。改為兩趟：先收集所有 cell 的聯集，再統一計分（同 §4.6 的守門精神）。⚠️ 因此本節 Gini **不可與 §4.7 直接比較** |

#### ① 結果（λ₁=0.5，hotspot，800 車，10 seeds，固定 ref 1,501 邊）

| λ₂ | ATT Δ | **Gini Δ** | worst-ρ Δ | Gini 絕對值 |
|---:|---:|---:|---:|---:|
| 0.0 | **−45.4** | −4.7 | −41.6 | 0.7204 |
| 0.3（計畫書預設） | −45.3 | −12.7 | −42.0 | 0.6601 |
| **0.8（現行）** | −44.0 | **−14.5** | −41.9 | 0.6462 |
| 1.5 / 3.0 / 6.0 | −43.0 / −41.8 / −40.6 | −15.9 / −17.1 / −18.3 | −42.3 / −42.6 / −43.2 | 0.6358 / 0.6263 / 0.6179 |
| **12.0** | −39.5 | **−19.1** | −43.2 | 0.6117 |

**主張成立，但不是天花板而是幾何遞減**：每加倍 λ₂ 買到的絕對 Gini 公比約 **0.81**，
等比外推漸近 **0.5851，即 Δ −22.6%**，仍差目標 7.4 pp。λ₂ 已是現行的 15 倍。

#### ② ★ λ₂ 買 Gini，λ₁ 買 worst-ρ——分工乾淨可分離

⑤（無懲罰）−3.3% → λ₂=0（只有 λ₁）−4.7% → 加 λ₂=0.8 **−14.5%**。
**λ₁ 只值 1.4 pp，λ₂ 一開就 10 pp。** 交叉確認：λ₁ 0.5→2.0 讓 worst-ρ 走 **4.4 pp**、
Gini 只動 0.4 pp，而在 λ₂=6.0 時兩個 λ₁ 的 Gini **完全相同**。
**這正是計畫書 eq.4 設計兩項的用意，現在有證據。**

#### ③ ★★★ 未達標的正確理由是拓樸，不是需求集中

| ⑥ 在 λ₂=12 | 平均出度 | 平均跳數 | 基準 Gini | **可達 Gini Δ** |
|---|---:|---:|---:|---:|
| **METR-LA / hotspot** | **76.22** | 1.47 | 0.87 | **−50.7%** ✅ 過門檻 |
| **台中 / hotspot** | **2.01** | 28.7 | 0.7558 | **−19.1%** |
| 台中 / random（同圖，需求打散） | 2.01 | 28.7 | 0.6407 | −16.0% |

**換需求動 3 pp，換圖動 32 pp——拓樸的影響是需求的十倍以上。**
而且打散需求讓相對改善**變差**：基準 Gini 本來就低，**分母小、百分比空間就小**。

**機制**：分流需要**平行的替代道路**。稠密相似度圖每節點 76 個鄰居、1.5 跳就到；
真實路網每節點 2 個出口（中位數 2、最大 4）、要走 28.7 跳。

🔴 **原本寫的「hotspot 灌向 4 個 hub 的不可避瓶頸」站不住**：那 16 條入邊只承載
**3.2%** 的逐邊行走量，釘的是 worst-ρ 的地板——而 worst-ρ 早已達標。
⛔ **「加大 `N_HOTSPOTS`」這條剩餘方向同時作廢**（random 是該方向的極端，結果更差）。

#### ④ 定案：不重訓 ⑦，並附上前緣

⑦ 捕捉 ⑥ 的 Gini 改善量約 56%，而 ⑥ 從 λ₂=0.8 到 12 只多 4.6 pp
→ **⑦ 預期只多 2.6 pp（−10.1% → 約 −12.7%），仍差 17 pp**，代價是 §4.7 之後所有
數字作廢。**這是計算，不是「反正達不到」的預感**——後者是拿 ⑥ 推 ⑦，而 **⑥ 不是 ⑦
在 Gini 上的上界**（實驗記錄 §14.1 ③ 有反例）。

⚠️ **但要誠實揭露 λ₂=0.8 不在 Gini 的效率點上**（λ₂=12 多 4.6 pp，代價 ATT +4.5 pp，
約 1:1）。正確處理是把整條前緣當作 ⑥ 的敏感度分析附上，並說明選 0.8 是為了 ATT、
且 ⑦ 是在該值上訓練的。

## 5. 耦合：預測 → 決策

```
202 個 TDX section 的預測速度
        │  一對多 map-matching（section_to_edges.csv）
        ▼
場域的邊
  ├─ 有 TDX 覆蓋（416 / 1,690）→ tpred = length / 預測速度
  └─ 無 TDX 覆蓋（1,274 / 1,690）→ 依 TAICHUNG_TPRED_FALLBACK
```

**map-matching 品質**：

| 指標 | v3（舊地圖） | **v4（`Map_fined`）** |
|---|---|---|
| TDX 路段總數 | 244 | 244 |
| 通過 300 m 門檻 | 212（86.9%） | **244（100%）** |
| 一對多路徑還原成功 | 209 / 212 | **237 / 244**（7 個退回單一邊） |
| 種子邊（全部路段） | 621 | **715** |
| 種子邊（存活的 202 路段） | 524 | **601** |

### 🔴 核心負面結果：預測層對路由沒有可測量的影響（v5：四個獨立佐證）

| # | 檢驗 | 結果 |
|---|---|---|
| (a) | 覆蓋率 15.2% → 24.6%（1.6 倍），10 seeds | **零變化**：①②③④ 的 worst-ρ 連標準差都相同（3.3302±0.2703） |
| (b) | 用 `t0` 與用 `tpred` 走出的路徑 | **86% 完全相同** |
| (c) | **換成 gated fusion**（實質不同的預測，15 分鐘 corr 0.985、中位差 3.04%，對照 hybrid↔stgat 的 0.998／0.97%） | ②③④ **仍疊在一起**；④ 在 S2 快 0.71%、S3 慢 1.44%，方向相反 = 雜訊 |
| (d) | **以 fusion 觀測重訓 agent** | 六個 Δ（S2/S3 × 三指標）**全部落在 1σ 內** |

**(c)(d) 是 v5 新增，也是最強的一對**——前兩個只換了覆蓋率或來源，這一次連 agent 都重訓了。

⚠️ **(d) 的限制**：兩個單次訓練的 agent 相比，無法分離「fusion 沒有影響」與
「PPO 的訓練變異蓋過了影響」。要分開得對每個來源各訓數個 seed。
**下方的結構論證是讓前者遠比後者可能的原因，報告應兩者並陳。**

**根因：Dijkstra 比的是時間 = 長度 / 速度，「按長度」的覆蓋率才是有效的那個。** 再簡化只改變邊的計數方式、不移除任何道路，所以**按長度的覆蓋率恆為 14.1%**。把路徑成本拆開（令 $m_e = t^{pred}_e / t^0_e$）：

$$\text{cost}_{pred} = \underbrace{2.035 \times \text{cost}_{t_0}}_{\text{均勻縮放}} + \underbrace{\sum_{e \in \text{有預測}} t^0_e (m_e - 2.035)}_{\text{唯一能改變排序的擾動}}$$

- 無預測的邊全部乘同一常數 2.035（`network_mean` fallback），**均勻縮放不改變路徑排序**。
- 有預測的邊 $m_e = 2.368 \pm 0.789$，但只佔路徑成本的 **14.1%**；一條 29 跳的路徑約經過 7 條有預測的邊，**擾動僅約路徑成本的 2%**，小於競爭路線之間的典型差距。

實測佐證：**用 `t0` 與用 `tpred` 走出完全相同路徑的比例 = 86%**。

### fallback 的兩難：消除偏差與保留訊號互相衝突

| 設定 | 有預測 vs 無預測 | 結果 |
|---|---|---|
| `free_flow` | 24.8 vs 50.5 km/h（差 2 倍） | 路由**系統性避開所有有資料的主幹道**，②③④ 比 ① 慢 18% |
| **`network_mean`（現行）** | 24.8 vs 24.9 km/h（對齊） | 偏差消除，**但訊號一起消失**，②③④ ≡ ① |

**兩種設定都無法讓預測正向影響決策**——這不是設定選錯，而是覆蓋率的本質限制：85% 的路網沒有觀測，任何 fallback 都只能是一個假設，而假設無論偏高、偏低或對齊，都不會產生資訊。

**「縮小場域拉高覆蓋率」這條路已實測失敗**：節點縮到 58%、按邊數的覆蓋率翻倍，②③④ 依然等於 ①。

> TDX 的 202 個路段對應約 600 條邊，而路網要**強連通且提供替代道路**至少需要 1,690 條邊。
> **預測永遠只能覆蓋路徑長度的一小部分。這是結構問題，不是程度問題。**

### 判讀：這反而強化了本專題的核心主張

在**預測貢獻可證明為零**的條件下，⑤⑥⑦ 仍達成大幅改善：

```
                     S2 尖峰漏斗                      S3 主幹道封閉
⑤ 只有協調      ATT −42.9%  ρ −36.2%  Gini −3.3%   ATT −60.4%  ρ −35.7%  Gini −7.7%
⑥ 協調 + eq.4   ATT −44.0%  ρ −41.9%  Gini −18.1%  ATT −61.2%  ρ −43.3%  Gini −17.4%
⑦ DRL（本系統）  ATT −36.0%  ρ −24.6%  Gini −10.1%  ATT −55.8%  ρ −27.5%  Gini −12.9%
```

計畫書的核心論點是「**問題出在決策機制，不在預測準確度**」。
**台中的證據比 METR-LA 更強——預測的邊際貢獻可量化為零，改善只能來自決策層。**

⚠️ **代價**：計畫書「預測 → 決策」的耦合在台中**沒有正向實證**。
**報告寫法**：主結果用 `network_mean`，附 `free_flow` 敏感度分析，明確揭露 14.1%（按長度）覆蓋率的限制，並以 METR-LA（100% 感測器覆蓋，ATT 0.1118 → 0.0349）佐證「覆蓋率足夠時預測確實會改變路由」。

## 9. 硬體與效能

### 9.1 訓練

**結論：現有 RTX 3080（10 GB）足夠，瓶頸不在 GPU。**

profiling（840 節點場域，800 車）：

| 項目 | 成本 | 判讀 |
|---|---|---|
| `_compute_enc_ctx` | 2.27 ms/車 → **1.8 s/episode** | 不是瓶頸 |
| `_observe` | 0.01 ms/步 → 0.4 s | 不是瓶頸 |
| **PPO update** | 800 車 × 48 步 × 4 epochs = **153,600 次獨立 GPU forward** | 🔴 **瓶頸** |
| VRAM | 4.2 / 10 GB，GPU 未飽和 | 加大 batch 無效 |

單次 forward 的運算是微秒級，但 **kernel launch 開銷約 50–100 µs**——時間幾乎全花在發射 15 萬次小工作上。**加大 batch size 不會減少發射次數**；正確做法是 **padding + masking 批次化**，或每 K 台車才重編碼一次。

> **場域再簡化（§4.1 步驟 ④）本身就是最有效的優化**：平均路徑 46.8 → 28.7 跳，
> transition 數直接少 39%，同時把「沒得選的決策點」從 54.5% 降下來——
> **既省時間又改善梯度品質。**

### 9.2 ★★ 推論延遲：計畫書 §5 的 <50 ms（v6 新增）

計畫書 §5 要求「DRL Agent 推論延遲**低於 50 ms（單次決策）**」。
量測方法與完整數據見實驗記錄 §13.25；此處只列方法論要點與結論。

#### 方法：三個讀法，不可用 rollout 總時間除以車數

`run_compare.py` 的執行時間是七個策略加 metrics 的總和；就算只取 ⑦ 那段，除以車數
得到的也是**吞吐量的倒數**。延遲必須分解，因為兩種成本的頻率不同、跳數本身又是變數
（S2 32.8 跳 / S3 40.3 跳，最大 79）：

```
單車路徑延遲 = [to-go Dijkstra]（每 togo_refresh 車一次）
             + [_compute_enc_ctx] + [ENCODE]（每車一次）
             + n_hops × ( [_observe] + [DECODE] + [step] )
```

**只有 ENCODE 與 DECODE 是模型推論**，其餘是狀態準備（部署時屬路況服務）。兩者分報。
「單次決策」的三個讀法——(a) 單跳、**(b) 單車完整路徑**、(c) 全隊重算——全部報告，
只報最便宜的 (a) 等於灌水。**一律報 p50/p90/p99/max**：`togo_refresh` 讓每車成本呈雙峰，
即時性的成敗在尾巴。

工具為 `integration/bench_latency.py`，計時器裝在**實例**上、`policies.py` 零改動，
並以 `--verify` 對照未包裝的 `policy_drl` 逐台車比對路徑（799/799 相同）。

#### 三項必須寫進報告的判讀

**① ✅ 計畫書 §5 達標，但只在貪婪解碼下。** 2,668 台車無一例外，且是把狀態準備
全部算進去的嚴格讀法。

**② 🔴 §4.5 定案「品質一律引用 beam-8」與 §5 直接衝突。** 兩個數字來自兩個設定，
**必須在同一段裡點明**，不能各取所需：貪婪 <50 ms 但 S3 放棄 17.2% 行程；
beam-8 救回行程（served 96.0%）但延遲 2–8 倍。

> 工程上有解：`beam_route` 目前每條 beam 各發射一次 `decode`（GPU 每車 218 次、
> 64.8 ms），8 條合批估可降到 27 次、~9.6 ms，端到端估 ~35 ms 即可過關。**未實作。**

**③ 🔴🔴 計畫書 §2.1 的前提在本場域不成立。** §2.1 主張「傳統演算法必須重複計算
全域最佳解，**計算成本高且無法即時反應**」——實測 ⑥ 一次請求只要 **0.31–0.33 ms**
（含攤提的 1,690 條邊重新定價），**比 ⑦ 快 43–68 倍，且 ATT / Gini / worst-ρ 三項全勝**。

> **因此 ⑦ 的定位不能建立在速度上，也不能宣稱勝過 ⑥。**
> 正確論述：**⑥ 是本場域成本函數（BPR + eq.4）的直接最佳化器**——它不是一個強基準，
> 它是解答本身；⑦ 是用梯度逼近一個已知的解析解，落後是結構上的必然。
> **⑦ 的價值主張只在成本函數不可解析時成立（SUMO / 真實路網），而那尚未驗證（§10 #17）。**
> 可主張的是：在只有 reward 的環境下學到 oracle **56%（S2）／74%（S3）** 的 Gini 改善，
> 且滿足即時性約束。

#### 兩個裝置選擇上的發現

**① 交叉點在每車 68–74 次解碼。** 1,690 條邊的編碼 GPU 快 8.9 倍（1.79 vs 15.88 ms），
但 ≤3 個候選的解碼 GPU 慢 2.9 倍（0.313 vs 0.107 ms）——後者純粹是 kernel launch 開銷，
是 §9.1 那個訓練端診斷在推論端的獨立重現。貪婪 23 次/車 → GPU 贏；
beam-8 261 次/車 → **CPU 贏 2 倍**。

**② GPU 平均快一倍，尾巴卻更糟**（max 45.09 vs 30.66 ms，距 50 ms 只剩 9.8% 餘裕）。
GPU 的成本集中在逐跳解碼、隨跳數長尾放大；CPU 集中在每車一次的編碼，是固定成本。
**對截止期限型的宣稱，CPU 是比較安全的裝置**——與「用 GPU 加速推論」的直覺相反。

#### 規模對照：完整路網（9,904 節點 / 27,022 邊）

E-GAT 的權重不含節點數，同一份 checkpoint 直接載到完整簡化路網上量 forward 成本
（路由品質在該尺度未經驗證，不宣稱）。每張圖 5 次不計時預熱 + 20 次計時，比值取中位數：

| `enc ctx`（Python 迴圈） | 0.751 → 11.948 ms　×15.9 | 1.155 → 11.910 ms　×10.3 |

GPU，27,022 條才開始用上。這與「小圖上 GPU 的解碼打不贏 CPU」是同一個現象的兩面。

**② 瓶頸是狀態準備，不是模型。** GPU 每車固定成本（與跳數無關）：

| | ms | 佔比 |
|---|---:|---:|
| `enc ctx`（逐節點 Python 迴圈） | 11.95 | 57% |
| **ENCODE（E-GAT）** | **7.69** | **36%** |

剩下 28.9 ms 約可容納 92 次解碼（≈115 跳）；場域平均 32.8 跳，完整路網的跳數**沒有量過**，
故此為算術而非量測。但方向明確：**買到餘裕的方法是向量化 `_compute_enc_ctx`，不是換小模型。**
同樣估算在 CPU 上是 183.6 ms——**完整路網上 GPU 從「較快」變成「必要」**，
裝置選擇因此隨規模與解碼寬度**兩個維度**翻轉。

**③ ⑥ 的優勢在這個尺度上仍然成立**：完整路網上一次 static Dijkstra 只要 6.3–7.1 ms，
仍遠低於 50 ms。**§2.1 的前提在本專題量得到的任何規模上都不成立**（見 §11 註記 D）。

> ⚠️ **報告只能引用其中一部分。** 場域 ENCODE 在 scale 區塊（GPU 4.209 / CPU 8.527 ms）
> 與 800 車 rollout（GPU 1.786 / CPU 15.884 ms）對不上，且**兩裝置方向相反**——GPU 未進

>

> （絕對值，不受分母影響）、瓶頸在狀態準備。

**核心論述（五句）**：

1. **環境真實、需求合成**——OSM 拓樸 + TDX 車速 + 車道容量皆為實測；需求因無真實 OD
   且需反事實比較而合成。所有策略在**完全相同的環境與需求**下對照，這是交通模擬研究的
   標準協定。

2. **問題出在決策機制，不在預測準確度**——在台中，預測對路由的邊際貢獻**可量化為零**
   （四個獨立佐證，§5），因為按長度的覆蓋率只有 14.1%。而協調與全域懲罰仍帶來
   **ATT −36%、worst-ρ −25%、Gini −10%**（事故情境下 ATT 更達 −56%）。
   **改善只能來自決策層。**

3. **羊群效應不只讓通行時間變差，還讓它變得不可預測**——未協調策略的 ATT 標準差為
   ±161.6，協調後降至 ±9.8（**16.4 倍**）。對導航服務而言，「今天多久到」無法估計
   本身就是嚴重的服務品質問題。

4. **未達標的那一項，是門檻本身不轉移**——Gini 目標 −30%，本系統 −10~−13%。
   **這不是學習不足，也不是「oracle 也達不到」這麼含糊**：把 eq.4 的擴散權重 λ₂ 拉到
   現行的 **15 倍**，解析最佳解也只到 **−19.1%**，增益幾何遞減、外推漸近 **−22.6%**。
   **原因是拓樸**：同一個門檻在 METR-LA 上達成了（⑥ −50.7%、⑦ −35.0%），那張圖每個節點
   有 **76** 個鄰居、平均 1.5 跳；台中真實路網只有 **2.01** 個出口、要走 28.7 跳。
   **分流需要平行的替代道路，而真實路網沒有那麼多。** 同一張圖上把需求打散只動 3 pp，
   換一張圖動 32 pp——**拓樸的影響是需求的十倍以上**（§4.9 ③）。
   **這個門檻是在稠密相似度圖上校準的，不轉移到真實路網。**

5. **即時性達標，但它不是本方法的賣點**——貪婪解碼下 2,668 台車**全部**低於 50 ms
   （計畫書 §5 ✅）。然而同一份量測顯示解析式 oracle 一次請求只要 **0.31 ms**，
   比本系統快 43–68 倍且三個指標全勝。**因此本系統不能以速度或「勝過 oracle」立論。**
   ⑥ 之所以又快又好，是因為**場域的成本函數（BPR + eq.4）就是它自己**——它是解答，
   不是近似。本系統的價值主張是「**在只有 reward、沒有解析成本模型的環境中，
   學到 oracle 五到七成的協調能力並滿足即時性約束**」，而那需要 SUMO 才能驗證（§9.2 ③）。
